# E0—E2 阶段审计工作记录

状态：历史记录。问题已由 E2.1-v2 修正设计、实施和冻结验收接续处理；本文不覆盖最终冻结结论。

## 已确认事实

- E0、E1、E2 均记录为 2026-10-08 冻结。
- E2 两端平台报告均为 `PLATFORM_PASS`，跨平台比较为 `CROSS_PLATFORM_PASS`。
- E0 覆盖共享契约、确定性数学、拓扑、容器积分、发布存储和独立 Python Oracle；E1 将球面空间身份、几何、拓扑、补丁和发布提升为正式层；E2 增加世界身份、主板块、边界运动资格和 M1 输入准入。
- 当前 Git 仓库没有提交历史，全部工程与文档文件均为未跟踪状态。

## 问题候选

- 冻结结果缺少 Git 提交或标签锚点。平台报告中的源码树 SHA-256 能验证受覆盖文件，但不能直接恢复完整仓库状态，也不覆盖全部文档和外围文件。
- **E0 跨平台同源性证据不足**：E0 平台报告没有 `source_tree_sha256`。macOS 报告包含 `python-version` 检查而 Windows 报告没有，JSON 文件计数分别为 17 和 15；比较器既不比较检查集合／测试数量，也不拒绝这些差异，却仍返回 `PASS`。这说明两份报告不是由完全相同的验证器状态产生，E0 的“双平台同源”冻结结论需要补强。
- **通用发布存储接受路径型身份**：`release-store` 直接将 `candidate_id`、`release_id` 和 `AssetId` 拼入文件路径，`world-contracts` 的字符串身份不做路径约束。E1/E2 的专用发布入口验证了候选和发布 ID，但通用 `write_field` 的 `AssetId` 仍缺少同类保护；未来 E3 若直接使用它，会存在越界写入或覆盖非预期路径的风险。
- **E0 资产头验证偏弱**：`AssetHeader::validate` 只检查依赖排序，没有检查重复依赖、空身份、摘要格式、空间范围、尺度上下界或单位完整性。JSON Schema 声明了一部分约束，但平台验证器只做 JSON 语法解析，没有执行 Schema 校验。
- **“原子发布”只验证可见性，没有验证崩溃持久性**：当前流程依赖同一存储根下的目录重命名，可保证候选与发布命名空间切换；没有文件及目录 `fsync` 证据，因此不应把它解释为断电后必然持久。
- **E1 自身也没有同源源码证明**：E1 比较器比较了报告状态、计数和一个很小的离散证据对象，但平台报告没有源码树摘要。离散证据只含身份版本、L0 的 24 条有向关系、面积容差字符串和空间清单摘要。E2 后来的源码树摘要覆盖当前 E1 源码，能补强“当前版本两端一致”，不能证明 E1 冻结报告生成时严格同源。
- **E1 冻结范围大于已实现查询契约**：方案把 `EdgeGeometry`、`resolve(cellId, requestedLevel)`、能力状态化查询、位置到补丁角色等列为最小能力；当前公开实现主要是 `locate`、单元 `geometry`、`active_cell`、精确 CellId 的 `patch_role` 与固定层球冠覆盖，没有 `EdgeGeometry` 类型，也没有返回 `QueryStatus` 的尺度解析接口。
- **空间发布对补丁语义的重建验证不足**：`validate_patches` 只检查目标层级、集合元素层级及 core/halo 不重叠，没有从 `core_parents` 重算 core、过渡叶和 halo，没有验证 2:1 邻接、支持环宽、父子谱系或集合完整性。重新计算摘要的伪造规范清单可能携带语义错误但通过打开验证。
- **固定件与测试没有程序化绑定**：E1F01—E1F08 和 PI01 只在平台脚本中做 JSON 语法解析；Rust 测试另行硬编码相似输入，没有加载固定件及断言其字段。固定件变化可能不改变真实测试，测试变化也可能与固定件描述漂移。
- **部分全称门槛只由少量样本支撑**：G02 以全 L4 邻接验证代表 L0—L30，G08 的 24 旋转只用一个单元，G09“球冠覆盖无假阴性”只测试一个球冠的有限采样，G01 的无碰撞也只抽取每层少数索引。算法结构看起来合理，但报告用“全部通过”表达的证明范围比测试覆盖更强。
- **可绕过构造器的不变量**：`SphericalCap`、`FaceCoord`、`PatchPlan` 等字段公开且可反序列化；`SphereQuery::new` 不重新验证补丁。库内正规路径会建立合法对象，但外部调用者可以构造超范围坐标、非法球冠或不一致补丁后进入查询。
- **E2 的 WorldSpec 未落实已确认的完整结构**：方案明确包含 `spatialReleaseId + spatialManifestHash`、完整 `modelManifest` 和可选 `fixedTestOverride`，实现只保存空间参考 ID 与一个构造模型版本。WorldId 因此没有绑定实际 E1 空间发布，也没有绑定固定测试覆盖模式；依赖摘要直到 M1 输入束才参与身份。
- **固定测试与随机构造共享生成身份**：构造模式由 CLI／函数参数决定而不属于 WorldSpec。同一种子可以生成固定 PV01 或普通随机构造，两者 `world_id` 与 `generation_identity` 相同，只有构造清单及后续输入束不同。若 `generation_identity` 被下游理解为自然生成身份，会发生语义碰撞。
- **活动度偏好破坏非目标属性隔离**：活动度偏好进入 WorldId；PlateId 从 WorldId 与站点派生；欧拉轴随机采样又以 PlateId 为实体键。因此仅改变活动度会改变 PlateId 和欧拉轴，等距 owner 裁决也可能改变。它没有做到方案要求的“活动偏好只调整运动幅度，不改变分区和欧拉轴身份”。
- **WorldSpec 的库边界没有强制验证**：CLI 读取文件时调用 `validate`，但 `WorldSpec::identity`、`NamedRandom::from_spec` 与 `tectonics_core::build` 不调用它。外部库调用者可以把不支持的 schema、模型、空间参考或未规范种子用于身份与构造。
- **E2 线程确定性检查无效**：验证器三次设置 `RAYON_NUM_THREADS=1/2/4`，但 workspace 没有 Rayon 依赖，构造实现是串行循环。这只能证明同一串行程序重复运行一致，不能证明不同线程调度一致。
- **E2 门槛状态是统一填充而非逐项证据**：平台验证器只要总检查、性能与三次一致性成功，就把 G01—G16 全部写成 `PASS`。没有门槛到测试／断言的机器可读映射，因此报告无法识别某个具体门槛其实未被执行。
- **PCAL 没有执行，报告表述过强**：验证器只检查 PCAL 和 PVAL 各含 32 个种子；基准程序只生成 PVAL。冻结报告称 PCAL/PVAL 均通过，但 PCAL 从未进入构造运行或统计输出。
- **E2 固定件仍未全面绑定测试**：E2F 与 E2I 多数只做 JSON 解析；少量等价断言在 Rust/Python 中另行硬编码。PV01 关系也是代码中硬编码检查，没有从 `PV01-E2-v1.json` 加载。固定件、实现测试与报告之间仍可能漂移。
- **M1 重开验证不足以证明语义一致**：`M1InputRelease::validate` 只检查 schema、三个交叉引用和 `STANDARD_GLOBAL` 必须拒绝。它不重算 InputBundleId、RunPlanId、AdmissionReport、能力矩阵、垂直基准、随机命名空间或依赖摘要。重新计算文件 SHA 后，错误的诊断／固定测试结论或被修改的输入字段可能通过 `open`。
- **M1 准入函数没有闭合 bundle 与 tectonic 的引用**：`admit(bundle, plan, tectonic)` 依据传入构造清单的状态和来源作决定，却不检查 bundle 是否引用该清单。正规 CLI 路径先正确构建 bundle，但公共 API 可把另一份 bundle 与当前构造清单组合成看似有效的准入报告。
- **构造中的部分离散裁决仍依赖未量化浮点**：20° 站点间距和板块面积阈值直接用 binary64 比较，并可能决定重试；方案要求所有会改变离散身份的连续裁决量化或处理不确定边界。当前 PVAL 跨两平台一致，但规则本身尚未完全落实。
- **固定资产清单状态与冻结结论矛盾**：`engine/fixtures/manifest.json` 仍写着 `E2_IMPLEMENTING`，而项目与验收报告写 E2 已冻结。该文件纳入 E2 源码树摘要，不能直接改动而不重做双平台报告。

## 疑问候选

- E0 是否需要以当前源码重新生成两端报告并加入源码树摘要，还是把 E0 明确降级为“技术路线已验证”，由 E1/E2 的强同源报告承接正式冻结信心？
- 身份合法性应由共享 `world-contracts` 统一定义，还是继续由各发布层各自验证？进入 E3 前必须统一，否则新资产类型容易遗漏路径约束。
- E1 冻结契约究竟冻结“当前已实现 API”，还是冻结方案中列出的完整 API？若以后补上缺失查询而不改变既有语义，可作为兼容扩展；若下游已经假设这些能力存在，则应先修正文档状态。
- 对球冠覆盖“无假阴性”的要求，是接受基于几何包围半径的算法论证加抽样，还是需要增加解析／高密度独立 Oracle 与跨面、极小、半球、近整球案例？
- WorldId、GenerationIdentity、构造发布 ID、InputBundleId 四者各自应承诺什么唯一性？必须先明确，才能决定固定测试模式和空间发布摘要放在哪一层。
- 高级偏好需要保证哪些非目标属性不变、哪些只要求统计单调？尤其活动度档位是否必须对同一板块保持轴不变、速率单调。
- M1 输入发布是“由可信进程创建后只做字节完整性检查”，还是“可从磁盘独立重建全部语义并拒绝伪造”？现有文档承诺后者，当前实现接近前者。

## 黑盒复现结果

- 活动度隔离：同一种子三档活动度生成相同站点集合，但 WorldId 和每块板块的欧拉轴均变化，确认 A02。
- M1 语义重建：把 `DIAGNOSTIC_ONLY` 改为 `ADMITTED` 并重新计算规范文件摘要后，CLI 验证仍返回 `VALID`，确认 A03。
- 临时复现目录：`/tmp/e2-activity-audit-codex`、`/tmp/e2-m1-forge-audit-codex`；均不属于工程源码树。

## 最终判断

- E0 技术路线可保留；E1 数学空间底座可继续使用；E2 的身份与 M1 契约需在 E3 前纠偏。
- 建议暂停 E3，建立 E2.1 纠偏方案，不直接修改当前冻结字节。
