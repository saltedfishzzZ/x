# E0—E2 阶段审计

> **文档状态**
>
> - 审计日期：2026-10-08
> - 审计范围：E0 工程底座、E1 球面空间层、E2 构造／M1 最小垂直切片
> - 审计方式：方案—实现—测试—平台报告四向核对，必要黑盒复现
> - 代码状态：本轮未修改引擎代码、测试、固定件或冻结报告
> - 总体结论：当前实现可以稳定重现既有 E2 原型，但存在三项进入 E3 前必须处理的契约问题；建议暂停 E3，建立 E2.1 纠偏方案

关联：[E0 实施方案](T0技术验证与E0工程底座实施方案.md) · [E1 实施方案](E1球面空间层实施方案.md) · [E2 实施方案](E2最小构造与M1实施方案.md) · [E2 冻结验收报告](../../engine/reports/e2/E2冻结验收报告.md)。

## 一、结论范围

本次审计没有发现现有测试中的运行失败。当前工作区通过：

- `cargo fmt --all -- --check`；
- 严格 Clippy；
- 60 项 Rust release 测试；
- 10 项独立 Python Oracle；
- E0、E1、E2 既有跨平台比较器；
- E2 当前源码树摘要复算，结果仍为 `94fd53c3f05c2e26827e357a5e08f4c9e5a8d0908425c643572987cd9c5069d1`。

因此现状不是“代码已经无法运行”，而是“现有测试通过，但若干冻结契约、验证边界和证据声明比实际实现更强”。E0 的技术路线、E1 的球面基础和 E2 的确定性原型仍有价值，不需要推倒重来。

## 二、已经可靠的部分

1. Rust 1.90.0 workspace、锁文件、离线构建、规范 JSON 和独立 Oracle 路线可用。
2. `cs1` CellId、父子关系、等角立方球面映射、L8 面积闭合、L4 全量邻接互反、局部切平面和空间发布具备可执行实现。
3. E2 的 L8 owner、板块连通、边界重建、整数运动资格、构造发布重开和 owner 损坏拒绝具备实质实现。
4. E2 的 macOS／Windows 报告确实绑定同一个源码树摘要，PV01 与 32 个 PVAL 世界的权威离散证据一致。
5. 普通世界仍明确限制为 `DIAGNOSTIC_ONLY`，材料、高程、海陆、气候、水文和正式地形没有被伪装成已实现。

## 三、进入 E3 前的阻断项

### A01：不同构造来源共享 GenerationIdentity

已确认的 E2 方案要求 WorldSpec 包含实际空间发布、模型清单和可选固定测试覆盖。当前 WorldSpec 只保存空间参考 ID 和单个构造模型版本，固定测试／随机构造由 WorldSpec 外部参数决定。

结果是：同一种子可以构造固定 PV01 或普通随机板块世界，但两者拥有相同 `world_id` 和 `generation_identity`。构造清单摘要及 M1 InputBundleId 最终仍不同，但 `generation_identity` 本身不再唯一描述自然生成输入。

进入 E3 前必须明确：

- WorldId 是否只代表用户世界意图；
- GenerationIdentity 是否必须绑定固定覆盖、空间发布和完整模型版本；
- 构造发布 ID 与 InputBundleId 分别承担哪一层内容唯一性。

在语义明确前，下游不能把 `generation_identity` 用作材料或高程缓存键。

### A02：活动度偏好改变欧拉轴及对象身份

方案要求活动度偏好只调整运动幅度，不改变板块分区和欧拉轴身份。当前活动度偏好进入 WorldId，PlateId 又由 WorldId 与站点派生，欧拉轴的命名随机实体键使用 PlateId。

黑盒复现显示，同一种子在 `Lower`、`Standard`、`Higher` 三档中拥有相同板块站点集合，但 WorldId、PlateId 排序和全部欧拉轴均变化。这会进一步影响速率随机分位，极少数等距 owner 的 PlateId 裁决也可能变化。

该问题会破坏高级偏好的单因素解释。修复时应把稳定板块角色键与完整 WorldId 分开，欧拉轴和速率分位绑定稳定角色；活动档位只映射同一分位到版本化幅度范围。

### A03：M1 可以接受语义篡改后重新签名的发布

当前 M1 重开验证只检查文件摘要、规范 JSON、schema、少量交叉引用，以及 `STANDARD_GLOBAL` 不得被接受。它没有重算 InputBundleId、RunPlanId、AdmissionReport、能力矩阵、垂直基准和依赖闭合。

黑盒复现步骤：

1. 正常生成 `DIAGNOSTIC` M1 发布，原结论为 `DIAGNOSTIC_ONLY`；
2. 把结论改为 `ADMITTED`；
3. 按规范 JSON 重新编码并更新 SHA-256；
4. 执行 `terrain-input validate`。

现有验证器返回 `VALID`。这证明当前摘要只能检测意外字节损坏，不能证明 M1 语义来自正式准入规则。

E3 会把 M1 作为正式上游输入，因此必须先让 `open/validate` 从发布内容重算所有派生身份、准入结论与能力，并验证 bundle 确实引用用于准入的构造清单。

## 四、重要缺口

### B01：E0／E1 的双平台同源证据不足

E0 两份报告没有源码树摘要，而且检查集合与 JSON 数量不同：macOS 为 17，Windows 为 15；macOS 报告还有 `python-version` 检查，Windows 报告没有。E0 比较器没有比较这些差异，仍返回 `PASS`。

E1 比较器比较测试计数和一个较小的离散证据对象，也没有源码树摘要。E2 后来的源码树摘要覆盖当前 E0/E1 代码，补强了当前版本的双平台一致性，但不能替代 E0/E1 各自冻结时的同源证据。

建议把 E0／E1 的结论解释为“技术与契约原型通过”，并在 E2.1 的统一平台验证器中纳入全树摘要和逐门槛证据，不必单独重跑已经被后续层覆盖的旧性能报告。

### B02：E1 方案中的查询契约没有全部实现

方案列出的 `EdgeGeometry`、`resolve(cellId, requestedLevel)`、能力状态化查询和位置到补丁角色没有完整实现。当前主要接口是定位、单元几何、活动叶、精确 CellId 的补丁角色和固定层球冠覆盖。

需要决定 E1 冻结的是“当前实现 API”还是“方案目标 API”。缺失能力若作为兼容扩展补齐，可以保留 `cs1`；文档不能继续把尚未实现的接口写成已冻结能力。

### B03：E1 补丁发布不能重建验证完整语义

空间发布验证只检查 core、transition 和 halo 的元素层级以及 core/halo 不重叠，没有从 `core_parents` 重算集合，也没有验证 2:1 邻接、halo 支持环和父子谱系。重新计算摘要的错误清单可能通过验证。

### B04：E2 的线程确定性门槛为空测

验证器设置 `RAYON_NUM_THREADS=1/2/4` 后三次运行相同命令，但工程没有 Rayon 依赖，构造路径是串行实现。这证明的是三次串行重复一致，尚未证明并行调度不改变结果。

在真正引入并行前，可以把门槛改为“串行重复确定性”；引入并行时再增加真实的执行器、分块顺序和归约树变形测试。

### B05：门槛、固定件与测试缺少机器可读追踪

E2 验证器在总检查成功后统一把 G01—G16 写为 `PASS`，没有逐门槛证据映射。E1F／E2F／E2I 多数只做 JSON 语法解析，Rust 与 Python 测试另行硬编码类似数据。

PCAL 只检查有 32 个种子，没有实际构造；PVAL 才进入基准程序。现有冻结报告中“PCAL/PVAL 均通过”的表述超出了实际证据。

### B06：部分领域对象可绕过构造器不变量

WorldSpec 的公共库入口不强制调用 `validate`；`SphericalCap`、`PatchPlan` 等可通过公开字段或反序列化产生非法状态；M1 公共构造函数也允许 bundle 与另一份 tectonic manifest 组合。正规 CLI 路径通常正确，但核心库契约尚未做到“非法状态不可进入”。

### B07：部分离散决定仍直接依赖 binary64

站点 20° 间距和板块面积 2%—35% 阈值可能决定有界重试，但使用直接浮点比较。当前 PVAL 在两平台一致，尚未触发实际差异；它仍不符合已确认的“身份相关连续裁决需量化或具有不确定边界”的规则。

## 五、工程与发布治理问题

1. 当前 Git 仓库没有任何提交，全部工程文件均未跟踪。冻结摘要能检查所选文件，却没有可恢复的提交或标签锚点。
2. 通用 `release-store` 直接将 candidate、release 和 AssetId 拼入路径。E1/E2 专用发布层检查了 candidate/release ID，通用 AssetId 仍无路径安全约束。
3. `AssetHeader::validate` 只检查依赖排序；空身份、重复依赖、摘要格式、空间范围和尺度关系没有统一验证。
4. 当前“原子发布”证明了目录重命名的可见性切换，没有文件和目录 `fsync` 证据，不应宣称断电持久性。
5. 固定资产登记文件仍标记 `E2_IMPLEMENTING`。该文件已进入 E2 源码摘要，修正状态后必须重新生成双平台报告。

## 六、需要共同决定的问题

1. **身份分层**：WorldId、GenerationIdentity、LayerReleaseId、InputBundleId 分别绑定哪些输入？固定测试覆盖属于哪一层？
2. **偏好隔离**：活动度、板块数量等高级偏好必须保持哪些属性不变？速率是否要求同一对象跨档位严格单调？
3. **冻结处理**：把 E2 标记为“带审计发现的冻结原型”，还是建立 `world-spec-v2`／`terrain-input-v2` 并保留 v1 只读兼容？
4. **验证信任边界**：磁盘发布是否必须独立证明语义，还是只允许受信进程生成、验证器仅检查字节完整性？现有设计文档倾向前者。
5. **E1 查询范围**：立即补齐方案承诺的查询状态与补丁重建，还是缩小 E1 冻结声明并把兼容扩展放到需要它的后续里程碑？
6. **并行策略**：E3 前是否引入真实并行，还是继续保持串行权威生成并把并行确定性门槛后移？

## 七、建议的纠偏顺序

建议建立 E2.1 纠偏里程碑，不进入材料与高程实现：

1. 冻结当前字节资产为只读基线，并建立可恢复的 Git 提交／标签；
2. 确认四类身份语义和偏好隔离矩阵；
3. 决定采用 v1 勘误还是新增 v2，禁止静默改变既有摘要；
4. 让 M1、空间补丁和共享资产头可从磁盘完整重建验证；
5. 将固定件直接加载进测试，并建立 G01—G17 到具体断言的映射；
6. 修正 PCAL、线程测试、离散量化和固定资产状态；
7. 重新运行 macOS／Windows 原生验证并生成新的统一审计报告；
8. 纠偏通过后，再设计 E3 M2／M3。

## 八、当前阶段判断

- **E0**：技术路线成立；冻结证据治理需要补强，但不阻止继续使用共享底座。
- **E1**：核心球面数学可继续作为上游；查询声明和补丁发布验证需要勘误或兼容补齐。
- **E2**：确定性构造原型成立；身份隔离和 M1 语义验证会直接影响 E3，必须先纠偏。

当前最合理的状态是：暂停 E3，保留 E0—E2 现有资产，不修改冻结字节。审计后的 E2.1-D01 至 D07 已记录于 [E2.1 修正设计与验收规范](E2.1修正设计与验收规范.md)，具体修改范围已整理为 [E2.1 代码实施方案](E2.1代码实施方案.md)；实施方案等待用户确认，确认前不修改引擎代码。
