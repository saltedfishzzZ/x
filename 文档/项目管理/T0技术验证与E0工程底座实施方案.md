## 一、目标

本阶段只完成两件事：

1. **T0 技术验证**：用最小、可丢弃实验验证 Rust 路线能否满足球面数值、确定性、拓扑、容器和存储要求。
2. **E0 工程底座**：只有 T0 通过后，才建立正式 Cargo workspace、共享契约、模式、资产身份、测试入口和原子发布骨架。

本阶段不生成正式随机地形，不实现构造板块、材料、高程、起伏、完整 M5/M6，也不创建桌面应用。

## 二、已知环境

当前工作区只有中文设计文档，尚无代码工程，也不是 Git 仓库。已检测到：

```text
rustc 1.90.0
cargo 1.90.0
Python 3.13.14
```

T0 建议先固定上述 Rust 版本，避免验证期间工具链漂移。Python 只承载独立 Oracle；其包版本在实际创建环境时锁定。是否初始化 Git 仓库属于 E0 的工程动作，需在开始实施时一并确认。

## 四、拟采用的依赖边界

首轮依赖保持精简：

| 用途 | 候选依赖 | 约束 |
| --- | --- | --- |
| 序列化 | `serde`、`serde_json` | 第三方类型不进入公开契约；规范化规则单独测试 |
| 错误 | `thiserror` 或等价轻量方案 | 错误编号由本项目拥有 |
| 摘要 | `sha2` | 语义摘要与字节摘要分开 |
| 命令行 | `clap` 或最小手写解析 | CLI 不进入核心层 |
| 并行验证 | `rayon` 或受控线程池 | 归约树、随机键和身份不依赖调度 |
| 数学 | `nalgebra` 或小型内部向量类型 | 先比较确定性和类型泄漏风险 |
| 压缩 | `zstd`，仅 TS05 | 可关闭，不影响语义摘要 |
| 属性测试 | `proptest` 或等价方案 | 固定失败种子并生成复现输入 |

Python Oracle 候选使用 `numpy`、`scipy`、`mpmath` 与 `pytest`，但每个 Oracle 必须说明独立性，不能调用 Rust 核心计算答案。

所有依赖在实际引入前检查许可证、跨平台构建、锁定能力和离线复现方式。没有通过检查的库不加入正式 workspace。

## 五、T0 执行顺序

### T0-01：最小工程壳

拟创建：根 workspace、工具链文件、基础格式检查、测试命令和一个只返回版本信息的 CLI。

目的：验证 Windows/macOS 使用相同工具链、锁文件和命令入口。此步骤不定义科学 API。

### T0-02：TS01 球面数值

拟实现最小内容：

- 等角立方球面正向／逆向映射；
- 三维单位向量和规范面选择；
- L0—L10 四叉键与父子关系；
- 跨面邻接、球面面积和大圆距离；
- 24 个立方体定向旋转；
- 一个 L10 补丁的核心、过渡和 halo 标记。

只运行 PF01/PF07/PF08 所需的几何断言，不实现自然地形。

### T0-03：TS02 确定性数学

拟验证：

- 命名随机键和无状态随机采样；
- 规范排序、固定归约树和补偿求和；
- 最小球谐系数生成与求值；
- 1／2／4 线程及正序／逆序／固定乱序分块；
- Windows/macOS 离散摘要与连续容差比较。

若标准数学库导致离散翻转，优先修改判定与误差区间，不自行实现整套超越函数；仍无法满足时再形成替代技术决定。

### T0-04：TS03 几何拓扑

拟在独立实验中实现：

- 规范三角分析面；
- 平台分量压缩；
- lower/upper link 分类；
- 并查集低位合并树；
- PF01、PF04、PF05、PF06 的离散拓扑断言。

本实验不实现正式 M5 数据模型，重点验证平台、并列鞍部、嵌套盆地和对象稳定排序是否可行。

### T0-05：TS04 容器积分

拟实现 PF03/PF06 的独立分片线性三角积分：

- 面积—势位与容积—势位曲线；
- 门槛事件节点；
- 嵌套排他区域；
- 曲线积分与直接空间积分比较；
- 非单调曲线故障注入。

本实验不分配水量、不生成湖泊或河流。

### T0-06：TS05 存储查询

拟验证：

- 规范 JSON 元数据；
- 小端 binary64 字段块；
- 稳定身份对象记录流；
- SHA-256 语义摘要与字节摘要；
- 可选压缩不改变语义摘要；
- 可重建索引；
- 临时候选到单一发布根的原子提交；
- 中断、字节篡改和索引删除测试。

### T0-07：技术决定门

汇总 TS01—TS05，逐项形成：

```text
结论：通过 / 有条件通过 / 失败
证据：测试、误差、跨平台差异、性能和复现入口
决定：正式采用 / 替换候选 / 回到规格修订
影响：E0 模块、模式、依赖与风险
```

只有五项形成可接受结论，才进入 E0。

## 六、E0 拟实现范围

T0 通过后，E0 将正式建立：

- `world-contracts`：单位、身份、状态、能力、错误和依赖引用；
- `sphere-core`：经过 TS01 验证的正式球面接口；
- `release-store`：资产头、规范内容、双摘要、候选与原子发布；
- `terrain-cli`：`inspect`、`validate` 和最小 `publish`，暂不提供真实 `generate`；
- 版本化模式与兼容性测试；
- PF/PV/PI 输入包的模式和加载器骨架；
- 结构化验收报告与复现包骨架；
- Windows/macOS 的相同构建及测试入口。

E0 不包含构造、材料和地形算法。这些从 E1/E2 开始进入正式实现。

## 八、测试与检查命令

实际命令名称可随 workspace 确认调整，但必须提供等价入口：

```text
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
python -m pytest engine/reference/python
terrain-cli validate <fixture>
terrain-cli inspect <asset-or-release>
```

跨平台比较工具必须读取两侧结构化结果，比较身份、离散关系、连续容差和失败编号，不能只比较终端文本。

## 九、T0/E0 退出条件

必须全部满足：

1. TS01—TS05 各有输入、结果、失败案例和技术决定记录；
2. Rust 路线能达到 P-D06 对应硬门槛，或已经记录并批准替代方案；
3. Windows/macOS 使用同一工具链策略、依赖锁和科学配置；
4. 核心模块依赖图无桌面、渲染、网络和水文依赖；
5. 规范内容的语义摘要跨存储重编码保持一致；
6. 中断写入和损坏资产不能成为正式发布；
7. 公开契约有版本、损坏输入和兼容性测试；
8. 所有未实现自然能力保持明确不可用；
9. 没有开始 E1 以后才拥有的自然生成逻辑；
10. 形成进入 E1 的具体实施建议，但不自动开始 E1。

## 十、实施期间的停止条件

出现以下情况时停止扩展并回到方案评审：

- 跨平台离散结果无法在统一判定规则下稳定；
- 球面面积、邻接或补丁聚合无法满足硬门槛；
- 拟采用序列化无法形成独立于压缩和路径的语义摘要；
- 拓扑或容器实验只能通过填洼、微扰平台或强选唯一出口完成；
- 依赖库迫使核心绑定桌面、数据库行身份或平台专有类型；
- T0 实验开始承载正式自然状态，导致实验与产品契约混淆；
- 需要修改已经确认的 P-D01—P-D07 语义才能继续。
